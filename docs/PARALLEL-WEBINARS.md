# План: два вебинара параллельно + вход в аккаунты из веб-интерфейса

Статус: **план** (6 июля 2026). Код не начат. Объединяет два запроса пользователя —
параллельная модерация двух вебинаров и управление Zoom-аккаунтами из веба.

## 1. Цель и ограничения

Бот должен модерировать **ровно 2 вебинара одновременно**.

**Жёсткое ограничение платформы:**
- Один Zoom-клиент может быть только в **одном** митинге.
- Один Zoom-аккаунт может быть только в **одном** активном митинге (второй вход
  выкидывает из первого).

Вывод: два параллельных вебинара = **два независимых bot-worker'а**, каждому нужна
**своя личность** — либо отдельный залогиненный аккаунт, либо гостевой вход (без
аккаунта, хост забирается по host-key).

## 2. Архитектура

```
                 ┌─────────────────────────────┐
   браузер ──────┤ web (FastAPI :8000)          │
                 │  реестр воркеров + вкладки    │
                 └───────┬───────────────┬──────┘
                         │               │
              http://bot-worker-1   http://bot-worker-2
                 (:9000, аккаунт A)     (:9001, аккаунт B / гость)
                    вебинар 1              вебинар 2
```

Каждый bot-worker изолирован в своём контейнере: свой Xvfb `:99`, свой PulseAudio
(vspeaker/vmic/BotMic), свой Zoom-клиент, свой `SessionManager`, рекордер, модератор,
музыка. Номер дисплея `:99` не конфликтует — контейнеры изолированы.

bot-worker **почти готов** к мультиинстансу: всё параметризуется через env
(порт, `SCREEN_GEOMETRY`, `ZOOM_BOT_NAME`, аккаунт). Основная работа — на стороне web.

## 3. Управление аккаунтами (веб) — включает запрос №2

Раздел «Аккаунты» в интерфейсе:

- **Добавить аккаунт**: email + пароль → хранится в БД (⚠️ пароль шифровать at-rest,
  ключ — из env/secrets; не класть в открытую).
- **Войти**: web триггерит на воркере flow логина (уже откалиброван —
  `gui.sign_in` → Zoom шлёт OTP на почту → web показывает поле OTP →
  `gui.enter_otp`). Статус: `не залогинен / ждёт OTP / залогинен`.
- **Ник по умолчанию**: глобальное поле. Приоритет имени в митинге:
  `ник события` → `ник по умолчанию` → текущий `«Модератор IPDC TG@telenokpetr»`.
- **Вход без аккаунта (гость)**: у события флаг «гость» → воркер входит по ссылке
  без логина, имя = ник, хост забирается по host-key.

**Персистентность логина (важно):** сейчас профиль Zoom (`~/.zoom`,
`~/.config/zoomus.conf`) НЕ в volume → при пересоздании контейнера логин и OTP
теряются. Смонтировать профиль как per-worker volume → «Stay signed in» переживёт
рестарты, OTP не нужен каждый раз. Это резко улучшает UX двух аккаунтов.

## 4. Изменения модели данных

- `accounts`: id, email, password_enc, display_name, status, created_at.
- `settings`: default_nickname (и прочие глобальные).
- `events` (существует): + `worker_id` (слот), + `account_id` (nullable → гость),
  + `nickname` (опц. переопределение).
- Реестр воркеров: статический конфиг из env `BOT_WORKER_URLS`
  (`http://bot-worker-1:9000,http://bot-worker-2:9001`), состояние (busy/free,
  текущее событие) — в памяти web + отражение в БД.

## 5. Изменения web

- `bot_client` параметризуется URL воркера (сейчас один `BASE`). Все вызовы —
  на нужный воркер по `worker_id`.
- Назначение: при старте события выбрать свободный слот, пометить busy; на leave —
  освободить. Ровно 2 слота.
- Эндпоинты: `/api/accounts/*` (CRUD, login, otp, status), `/api/settings`,
  а `/api/bot/*` получают селектор воркера (напр. `/api/bot/{worker_id}/...`).
- Планировщик учитывает занятость слотов (нельзя запустить 3-й параллельно).

## 6. Изменения bot-worker

- Новые эндпоинты `/account/sign-in` (email,pass), `/account/otp` (code),
  `/account/status` — поверх откалиброванных `gui.sign_in`/`gui.enter_otp`.
- Join: принимать контекст (залогинен / гость + ник); ставить ник при входе.
- Надёжная установка ника (кириллица) — портировать метод через буфер обмена
  (`xclip` + Ctrl+V), проверенный вживую (см. историю калибровки).
- Профиль Zoom — per-worker volume (см. §3).

## 7. UI: вкладки по вебинару

- Панель вкладок: «Вебинар 1» / «Вебинар 2» (по слоту-воркеру). В каждой —
  свой live-просмотр, статус сессии, контролы записи/модерации/музыки/Mute,
  своя лента модерации.
- Общие разделы: «Аккаунты», «Мероприятия» (расписание с выбором слота/аккаунта/ника).
- Текущая одиночная панель становится шаблоном вкладки, параметризованным `worker_id`.

## 8. Деплой (compose)

- Добавить сервис `bot-worker-2` (тот же образ, порт 9001, свои volume:
  `recordings-2`, `music-2`, `zoomprofile-1/2`).
- web env: `BOT_WORKER_URLS=http://bot-worker-1:9000,http://bot-worker-2:9001`.
- Ресурсы: два Zoom-клиента + два Xvfb ≈ 2× CPU/RAM, `shm_size: 1gb` каждому —
  проверить, что хост тянет.

5. **Проверка**: два одновременных митинга под двумя аккаунтами.

## 10. Риски / открытые вопросы

- **Безопасность паролей** аккаунтов: шифрование at-rest, ключ вне репозитория.
- **OTP-трение** при первом входе / после потери профиля — смягчается volume-профилем.
- **Ресурсы**: 2× клиент Zoom — нагрузка на хост.
- ~~**Webinar vs Meeting**~~ — **решено (6 июля 2026): это обычные митинги**, не Zoom
  Webinars. Значит существующие хост-контролы (Mute All, модерация чата, запись,
  музыка) применяются как есть, ролей панелист/зритель нет. Термин «вебинар» в UI/доке
  = обычная конференция.
